## 📝核心概念与原理

### 一、死锁的定义

> **死锁（Deadlock）**是指两个或两个以上的进程在执行过程中，因争夺资源而造成的一种**互相等待**的现象，若无外力作用，这些进程都将**无法向前推进**。

**关键理解**：死锁中的进程处于"阻塞"状态，不是因为等待I/O，而是因为等待**永远不会发生的资源**。

### 二、产生死锁的原因

#### 1. 系统原因

- **资源不足**：系统中可供共享的资源数量有限
- **进程推进顺序不当**：进程请求和释放资源的顺序不合理

#### 2. 程序原因

- 进程并发执行时，对共享资源的竞争
- 进程推进顺序不合理

### 三、死锁产生的四个必要条件 ⭐ 🔥

这四个条件**同时满足**才会产生死锁，缺一不可。

| 条件 | 说明 | 示例 |
|------|------|------|
| **1. 互斥条件** | 资源一次只能被一个进程使用 | 打印机、信号量 |
| **2. 请求与保持条件** | 进程保持已获得资源，同时请求新资源 | 进程A持有R1，请求R2 |
| **3. 不剥夺条件** | 进程已获得资源在未使用完前，不被剥夺 | 进程A释放R1由自己决定 |
| **4. 循环等待条件** | 存在一个进程等待环：P1→R1→P2→R2→P1 | 进程形成环路 |

> ⭐ **选择题考点**：只要破坏上述**任意一个**条件，就能避免死锁。这是死锁预防的核心思想。

### 四、资源分配图（Resource Allocation Graph）

#### 1. 资源分配图的结构

```
进程节点：□ (方框表示进程)
资源节点：○ (圆圈表示资源)
           ● (圈中的小点表示该类资源的实例数)

请求边：→ (进程→资源，表示进程请求该资源)
分配边：← (资源→进程，表示资源已分配给进程)
```

#### 2. 利用资源分配图判断死锁

**情况一：无环 → 无死锁**

```
P1 → R1 ← P2   (只有P2持有R1，P1等待R1但R1只有一个实例且被P2持有，但P2不等待任何资源)
```

**情况二：有环 → 可能死锁**

- 如果每个资源类只有**一个实例**：有环 ⇔ 死锁
- 如果资源类有**多个实例**：有环 ⇒ 可能死锁（不一定是死锁）

> ⭐ **选择题考点**：资源分配图中，当且仅当每个资源类只有一个实例时，"有环"是死锁的充分必要条件。

**资源分配图简化（化简）规则**：
1. 找出一个既不在边也不在简化图中的进程节点Pi
2. 如果Pi请求的资源都能被满足（资源剩余数 ≥ Pi请求数），则Pi可获得所有资源并完成执行
3. 将Pi以及与之关联的所有边删去（Pi完成）
4. 重复上述过程，如果所有进程都能被删去，则无死锁；否则存在死锁

### 五、死锁的处理策略

| 策略 | 核心思想 | 是否常用 | 优点 | 缺点 |
|------|---------|---------|------|------|
| **死锁预防** | 破坏四个必要条件之一 | 常用 | 简单、可靠 | 资源利用率低 |
| **死锁避免** | 动态检查资源分配，确保系统不进入不安全状态 | 较常用 | 资源利用率较高 | 实现复杂 |
| **死锁检测与解除** | 允许死锁发生，定期检测并解除 | 不常用 | 资源利用率高 | 需要额外开销 |
| **死锁忽略** | 认为死锁极少发生，不采取措施 | 不常用 | 开销最小 | 可能发生死锁 |

> 策略选择：UNIX系统通常采用"忽略"策略（Ostrich算法）；数据库系统采用"检测与解除"策略。

### 六、死锁预防（破坏必要条件） 🔥

#### 1. 破坏"互斥条件"

**方法**：将独占资源改造为共享资源。

**问题**：许多资源无法改造为共享资源（如打印机必须互斥使用），因此此方法**实用性很差**。

#### 2. 破坏"请求与保持条件"

**方法一：静态分配（预先分配）**
- 进程在运行前一次性申请所有需要的资源
- 若某些资源不能满足，则不分配任何资源，进程阻塞等待

**方法二：动态分配**
- 进程在整个运行期间不能持有资源
- 获得新资源前必须释放已持有的资源

> 问题：资源利用率低，可能引起**饥饿**。

#### 3. 破坏"不剥夺条件"

**方法**：
- 进程已获得某些资源后，若再请求新资源不被满足，则必须释放已占有的资源
- 或者由OS剥夺已分配的资源

> 问题：适用于易剥夺资源（如CPU寄存器），不适用于打印机等资源。

#### 4. 破坏"循环等待条件" ⭐

**方法：有序资源分配法**

将系统中所有资源类型实行编号（R1, R2, ..., Rn），规定进程必须按编号递增的顺序请求资源。

**示例**：

```
资源编号：R1 < R2 < R3

正确请求：
    P请求R2 → 获得 → P请求R3（符合递增顺序 ✓）

错误请求：
    P请求R3 → 获得 → P请求R2（违反递增顺序 ✗）
```

> ⭐ **选择题考点**：有序资源分配法破坏了"循环等待条件"。它要求进程按资源编号递增顺序请求资源，从而不可能形成循环等待。

### 七、死锁避免（银行家算法） 🔥🔥🔥

#### 1. 安全状态与不安全状态

**安全状态（Safe State）**：

> 如果系统能按某种进程推进顺序{P1, P2, ..., Pn}，为每个进程Pi分配其所需的资源，直至满足Pi对资源的最大需求，使Pi能够顺利执行完毕，则称系统处于安全状态。

**不安全状态（Unsafe State）**：

> 若不存在一个安全序列，则系统处于不安全状态。

> **关键理解**：安全状态 ≠ 一定不发生死锁；不安全状态 ≠ 一定发生死锁。但不安全状态**有可能**导致死锁。

#### 2. 银行家算法（Banker's Algorithm）

银行家算法的核心思想：在分配资源之前，先检查分配后系统是否仍处于安全状态。如果是，才分配；否则，进程等待。

#### 3. 数据结构

| 数据结构 | 定义 | 说明 |
|---------|------|------|
| Max[n][m] | n个进程对m类资源的最大需求 | 每个进程最多需要多少资源 |
| Allocation[n][m] | 已分配资源数 | 当前分配给每个进程的资源 |
| Need[n][m] | 还需要资源数 | Need = Max - Allocation |
| Available[m] | 可用资源数 | 系统中每类资源当前的剩余数量 |

#### 4. 银行家算法步骤

```
假设进程Pi提出请求资源Request：

步骤1：如果 Request[i] ≤ Need[i]，转步骤2；否则报错（请求超过最大需求）

步骤2：如果 Request[i] ≤ Available[i]，转步骤3；否则进程Pi等待

步骤3：系统尝试分配资源：
        Available = Available - Request[i]
        Allocation[i] = Allocation[i] + Request[i]
        Need[i] = Need[i] - Request[i]

步骤4：执行安全性算法检查：
        如果系统安全 → 分配成功
        如果系统不安全 → 恢复分配（回溯），进程Pi等待

步骤5：如果安全，则将资源分配给进程Pi；否则，Pi等待
```

#### 5. 安全性算法（Safety Algorithm）

```
步骤1：设置两个向量
    Work[m] = Available[m]     // 工作向量，初始为Available
    Finish[n] = false           // 记录每个进程是否完成

步骤2：从进程集合中找到一个满足以下条件的进程Pi：
    a. Finish[i] = false
    b. Need[i] ≤ Work[i]       // 该进程所需资源不超过Work

步骤3：若找到Pi：
    Work[i] = Work[i] + Allocation[i]    // 释放Pi占用的资源
    Finish[i] = true
    返回步骤2

步骤4：所有进程的Finish[i]都为true，则系统处于安全状态
```

> **安全序列**：如果存在一个进程序列{P1, P2, ..., Pn}，使得每个进程都能获得所需资源并完成执行，则该序列称为安全序列。存在安全序列 ⇔ 系统处于安全状态。

#### 6. 银行家算法示例（大题）

假设系统中有3类资源（A, B, C），数量分别为（10, 5, 7）。在T0时刻：

| 进程 | Allocation(A,B,C) | Max(A,B,C) | Need(A,B,C) |
|------|-------------------|------------|-------------|
| P0 | (0, 1, 0) | (7, 5, 3) | (7, 4, 3) |
| P1 | (2, 0, 0) | (3, 2, 2) | (1, 2, 2) |
| P2 | (3, 0, 2) | (9, 0, 2) | (6, 0, 0) |
| P3 | (2, 1, 1) | (2, 2, 2) | (0, 1, 1) |
| P4 | (0, 0, 2) | (4, 3, 3) | (4, 3, 1) |

Available = (1, 1, 2)

**T0时刻安全性检查**：

```
初始：Work = (1, 1, 2), Finish = [F, F, F, F, F]

第1轮：
  P0: Need(7,4,3) > Work(1,1,2) → 不满足
  P1: Need(1,2,2) > Work(1,1,2) → B资源不够，不满足
  P2: Need(6,0,0) > Work(1,1,2) → A资源不够，不满足
  P3: Need(0,1,1) ≤ Work(1,1,2) → 满足！
      Work = Work + Allocation(P3) = (1,1,2) + (2,1,1) = (3,2,3)
      Finish[3] = true

第2轮：
  P0: Need(7,4,3) > Work(3,2,3) → 不满足
  P1: Need(1,2,2) ≤ Work(3,2,3) → 满足！
      Work = (3,2,3) + (2,0,0) = (5,2,3)
      Finish[1] = true

第3轮：
  P0: Need(7,4,3) > Work(5,2,3) → 不满足
  P2: Need(6,0,0) > Work(5,2,3) → A资源不够，不满足
  P4: Need(4,3,1) > Work(5,2,3) → B资源不够，不满足

第4轮：
  P0: Need(7,4,3) > Work(5,2,3) → 仍不满足...

  等待，继续寻找：
  P2: Need(6,0,0) > Work(5,2,3) → A不够
  P4: Need(4,3,1) ≤ Work(5,2,3) → B不够...

  重新检查：
  P4: Need(4,3,1)，Work(5,2,3)，3 > 2 → 不满足
  P0: Need(7,4,3)，Work(5,2,3)，7 > 5 → 不满足
  P2: Need(6,0,0)，Work(5,2,3)，6 > 5 → 不满足

  无法找到满足条件的进程 → 系统处于不安全状态？
  
  等等，让我重新计算...
  
  实际上：
  Work = (3, 2, 3)
  P1: Need(1,2,2) ≤ (3,2,3) ✓ → Work = (3+2, 2+0, 3+0) = (5,2,3)
  
  现在Work = (5,2,3)
  P0: Need(7,4,3) ≤ (5,2,3)? 7>5, 4>2 → ✗
  P2: Need(6,0,0) ≤ (5,2,3)? 6>5 → ✗
  P4: Need(4,3,1) ≤ (5,2,3)? 4≤5, 3>2 → ✗
  
  所有进程都无法满足 → 死锁？
  
  让我重新分析...
  
  其实T0时，应该先从P3开始：
  P3: Need(0,1,1) ≤ (1,1,2) ✓
  Work = (1,1,2) + (2,1,1) = (3,2,3)
  
  P1: Need(1,2,2) ≤ (3,2,3) ✓
  Work = (3,2,3) + (2,0,0) = (5,2,3)
  
  P4: Need(4,3,1) ≤ (5,2,3)? 3 > 2 ✗
  P0: Need(7,4,3) ≤ (5,2,3)? 7 > 5, 4 > 2 ✗
  P2: Need(6,0,0) ≤ (5,2,3)? 6 > 5 ✗
  
  继续尝试P4、P0、P2，都不满足...
  
  所以当前Available = (1,1,2)时，如果从P3→P1→?，后续卡住。
  
  换个顺序试试：
  P3 → 获得后 Work = (3,2,3)
  P1 → 获得后 Work = (5,2,3)
  P2: Need(6,0,0) ≤ (5,2,3)? 6 > 5 ✗
  P4: Need(4,3,1) ≤ (5,2,3)? 3 > 2 ✗
  P0: Need(7,4,3) ≤ (5,2,3)? 7 > 5 ✗
  
  确实，如果Available = (1,1,2)，系统可能处于不安全状态。
```

> **注意**：实际考试中需要仔细计算，确保每个步骤正确。银行家算法的计算过程是408考试的**必考大题**。

### 八、死锁的检测与解除

#### 1. 死锁的检测

**单类资源**：利用资源分配图简化判断

**多类资源**：利用死锁检测算法

```
步骤1：从Wait-For图中查找环
步骤2：如果找到环，则存在死锁
步骤3：环中的进程为死锁进程
```

#### 2. 死锁的解除

| 方法 | 说明 | 代价 |
|------|------|------|
| **资源剥夺** | 从死锁进程中抢占资源，分配给其他进程 | 可能回滚进程 |
| **撤销进程** | 终止所有死锁进程或逐个终止 | 可能损失大量计算结果 |
| **进程回滚** | 让进程回滚到某个检查点 | 需要保存检查点 |

## ⚖️易混淆概念对比

### 死锁预防 vs 死锁避免

| 对比项 | 死锁预防 | 死锁避免 |
|--------|---------|---------|
| 核心思想 | 破坏四个必要条件之一 | 动态检查系统是否处于安全状态 |
| 实施时机 | 静态（设计时确定策略） | 动态（运行时实时检查） |
| 资源利用率 | 较低（限制严格） | 较高（仅在必要时阻塞） |
| 实现复杂度 | 简单 | 复杂（需要银行家算法） |
| 代表方法 | 有序资源分配法 | 银行家算法 |

### 安全状态 vs 死锁

| 概念 | 定义 | 关系 |
|------|------|------|
| 安全状态 | 存在一个安全序列，所有进程都能完成 | 安全状态 ≠ 一定无死锁（只是确保无死锁） |
| 不安全状态 | 不存在安全序列 | 不安全状态 ≠ 一定发生死锁（只是有可能） |
| 死锁 | 进程互相等待，无法推进 | 安全状态一定不死锁；不安全状态可能死锁 |

## ⚠️考试高频坑点

### 坑点1：死锁四个必要条件必须同时满足 ⭐

> 【教材原文】死锁的四个条件必须**同时满足**才会产生死锁。
>
> 【考试考法】选择题常问"下列哪个条件不是死锁产生的必要条件"，选项可能包含"竞争条件"等干扰项。

### 坑点2：银行家算法的安全性判断 ⭐

> 【考试考法】给出资源分配矩阵和进程需求，判断系统是否处于安全状态。
> 关键步骤：
> 1. 计算Need = Max - Allocation
> 2. 从Available开始寻找满足Need ≤ Work的进程
> 3. 逐步释放资源，看能否找到一个安全序列

### 坑点3：安全状态 ≠ 无死锁

> 【教材原文】系统处于安全状态，一定不会产生死锁；但不安全状态不一定会产生死锁，只是**有可能**产生。
>
> 【考试考法】判断题："系统处于不安全状态则一定发生死锁"——答案是**错误**。

### 坑点4：有序资源分配法破坏了哪个条件

> 【考试考法】选择题问"有序资源分配法破坏了死锁的哪个条件"，答案是**循环等待条件**。
