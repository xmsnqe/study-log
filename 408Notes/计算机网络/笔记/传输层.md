# 05 传输层（Transport Layer）

> 📌 传输层是408计算机考研的**核心大题模块**，TCP三次握手、拥塞控制、滑动窗口等是必考内容。

---

## 📍知识定位

| 维度 | 说明 |
|------|------|
| **在408体系中的位置** | 自顶向下五层模型的第4层，为应用层提供**端到端（进程到进程）**的通信服务 |
| **学习前置条件** | 网络层（IP转发）、数据链路层 |
| **支撑后续知识点** | 应用层协议（HTTP/DNS/SMTP等）、网络安全（TLS） |
| **跨教材视角** | 《自顶向下》以TCP/UDP为核心展开；CSAPP从进程、文件描述符、socket API角度补充；谢希仁《计算机网络》补充拥塞控制与流量控制的对比 |

---

## 📝核心概念与原理

### 一、传输层服务概述

传输层向应用层提供以下两种核心服务：

| 服务类型 | 特点 | 协议 |
|---------|------|------|
| **TCP（Transmission Control Protocol）** | 可靠传输、面向连接、字节流、流量控制、拥塞控制 | TCP |
| **UDP（User Datagram Protocol）** | 不可靠传输、无连接、报文段、尽力而为 | UDP |

> **⭐选择题高频考点**：
> - TCP提供**可靠的、面向连接的、全双工**的字节流服务
> - UDP提供**不可靠的、无连接的**报文服务
> - 传输层复用/分用：通过**端口号**区分不同进程

---

### 二、端口号（Port Number）⭐

端口号：16位，范围 0~65535

| 端口范围 | 说明 | 典型端口 |
|---------|------|---------|
| 0~1023 | 熟知端口（Well-Known Ports） | HTTP:80, HTTPS:443, DNS:53, SSH:22, SMTP:25, FTP:21 |
| 1024~49151 | 注册端口（Registered Ports） | 应用程序自定义 |
| 49152~65535 | 临时端口/动态端口（Ephemeral Ports） | 客户端自动分配 |

```
传输层复用与分用：

发送方复用：
  进程A（端口52000） ──┐
  进程B（端口52001） ──┼──→ TCP/UDP 模块 → 网络层 → 分组发送
  进程C（端口52002） ──┘

接收方分用：
  分组到达 → TCP/UDP 模块 → 根据目的端口号分发给对应进程
  目的端口52000 → 进程A
  目的端口52001 → 进程B
  目的端口52002 → 进程C
```

> **⭐选择题高频考点**：传输层通过**端口号**实现端到端的进程通信，而网络层通过IP地址实现主机到主机的通信。

---

### 三、UDP协议 ⭐

**UDP（用户数据报协议）**：无连接、不可靠、尽最大努力交付

```
UDP报文段格式（固定8字节头部）：
┌─────────────────────────────────────────┐
│  源端口（16位）    │  目的端口（16位）    │
├─────────────────────────────────────────┤
│       长度（16位）     │     校验和（16位）   │
├─────────────────────────────────────────┤
│              数据（可变长度）              │
└─────────────────────────────────────────┘
```

**UDP特性**：
- 头部仅8字节（TCP为20字节起）
- 无连接建立/释放开销
- 无拥塞控制
- 支持**一对多、多对一、一对多**的通信（广播/多播）
- 报文边界保持：UDP不合并报文，应用层发几次，接收方就收几次

> **⭐选择题高频考点**：UDP校验和计算时使用**伪首部**（源IP、目的IP、协议号、UDP长度），但UDP校验和是可选的（IPv4中为0表示无校验）。

---

### 四、TCP协议 ⭐

#### 4.1 TCP报文段格式 🔥

```
TCP报文段格式（最小20字节）：
┌─────────────────────────────────────────┐
│  源端口（16位）    │  目的端口（16位）    │  ← 标识通信进程
├─────────────────────────────────────────┤
│       序号（32位）                        │  ← 字节流序号，标记数据起始位置
├─────────────────────────────────────────┤
│    确认序号（32位）                       │  ← 期望收到的下一个字节序号
├─────────────────────────────────────────┤
│  数据偏移（4位）│  保留（6位）│  CWR ECE SYN RST URG PSH ACK FIN │
│              (TCP头部长度)              │  ← 控制位
├─────────────────────────────────────────┤
│       窗口大小（16位）                    │  ← 流量控制（接收窗口）
├─────────────────────────────────────────┤
│       校验和（16位）                      │  ← 可靠性保障
├─────────────────────────────────────────┤
│       紧急指针（16位）                    │  ← 紧急数据位置
├─────────────────────────────────────────┤
│              选项（可变长度）              │  ← MSS、窗口扩大因子等
├─────────────────────────────────────────┤
│               数据（可变长度）              │
└─────────────────────────────────────────┘
```

**TCP控制位（标志位）**：

| 标志位 | 名称 | 说明 |
|-------|------|------|
| URG | URGENT | 紧急指针有效 |
| ACK | ACKNOWLEDGMENT | 确认序号有效 |
| PSH | PUSH | 推送，要求立即交付给上层 |
| RST | RESET | 连接重置（异常） |
| SYN | Synchronize | 同步序号（连接建立） |
| FIN | FINISH | 结束（连接释放） |

> **⭐选择题高频考点**：
> - SYN报文段**不携带数据**但消耗1个序号
> - FIN报文段**不携带数据**但消耗1个序号
> - ACK报文段通常携带数据

#### 4.2 TCP连接管理 🔥（大题高频）

##### 4.2.1 三次握手（Three-Way Handshake）

```
客户端                          服务器
  │                               │
  │  SYN=1, seq=x                 │  (1) 发送SYN
  │──────────────────────────────→│
  │                               │
  │  SYN=1, ACK=1                 │  (2) 回复SYN+ACK
  │  seq=y, ack=x+1               │
  │←──────────────────────────────│
  │                               │
  │  ACK=1                        │  (3) 确认
  │  seq=x+1, ack=y+1             │
  │──────────────────────────────→│
  │                               │
  │  连接建立完成                   │
  │                               │
```

> **⭐选择题高频考点**：
> - 为什么是三次握手而不是两次？**防止已失效的连接请求报文段突然又到达服务器**，导致服务器错误地建立连接
> - 第二次握手服务器发送 **SYN+ACK** 两个标志位
> - 三次握手期间可以携带数据：第三次握手的ACK可以携带数据，前两次的ACK也可以携带数据

##### 4.2.2 四次挥手（Four-Way Termination）

```
客户端                          服务器
  │                               │
  │  FIN=1, seq=u                 │  (1) 发送FIN（主动关闭）
  │──────────────────────────────→│
  │                               │
  │  ACK=1                        │  (2) 确认（半关闭状态）
  │  seq=v, ack=u+1               │
  │←──────────────────────────────│
  │                               │
  │                               │  (3) 服务器数据发送完毕后发FIN
  │  FIN=1, ACK=1, seq=w, ack=u+1 │
  │←──────────────────────────────│
  │                               │
  │  ACK=1                        │  (4) 确认
  │  seq=u+1, ack=w+1             │
  │──────────────────────────────→│
  │                               │
  │  等待2MSL后关闭                  │  ← 2MSL等待时间
  │                               │
```

> **🔥大题高频考点**：
> - 为什么挥手需要四次？因为TCP是全双工的，**每一方都需要单独关闭自己的方向**
> - 为什么客户端需要等待2MSL？**①保证最后一个ACK能到达服务器；②让本连接持续时间内产生的所有报文段都从网络中消失**
> - 2MSL = 最大报文段生存时间 × 2 = 通常 2分钟（MSL通常为2分钟）

#### 4.3 TCP可靠传输 🔥

**核心机制**：

| 机制 | 说明 |
|------|------|
| **序号机制** | 每个字节数据有一个序号，接收方根据序号排序、去重 |
| **超时重传** | 发送方为每个报文段设置定时器，超时则重传 |
| **累积确认** | 确认序号表示"该序号之前所有数据已正确收到" |
| **校验和** | 发送方计算校验和，接收方验证 |

**超时时间（RTO）的计算：**

```
RTT_sample = 从发送报文段到收到确认的时间差（采样）

RTO = α × RTO_prev + (1-α) × RTT_sample   （通常α=0.875）

RTO >= 1.3 × RTT_sample + max(4, K) ms

K = 往返传播延迟的估测值
```

> **⭐选择题高频考点**：TCP的超时重传时间不是固定值，而是动态调整的，基于**RTT的平滑加权平均**。

---

#### 4.4 TCP流量控制 ⭐

**流量控制（Flow Control）**：防止**发送方发送太快**导致**接收方缓冲区溢出**

**核心机制：滑动窗口（Sliding Window）**

```
接收方通过TCP报文段的"窗口大小"字段告知发送方自己还能接收多少数据

发送窗口（sender window）：
  ┌────── 接收窗口（rwnd） ──────┐
  │ ←─────────────── │
  │ 已发送未确认 │  已确认  │ 空闲  │
  │ ← 发送窗口 → │ ←────────→ │
  │ 由rwnd和cwnd共同决定大小     │

发送窗口大小 = min(接收窗口rwnd, 拥塞窗口cwnd)
```

- **rwnd（Receive Window）**：由接收方通告，表示接收方缓冲区剩余空间
- **cwnd（Congestion Window）**：由发送方估算，表示网络拥塞程度
- **发送窗口 = min(rwnd, cwnd)**：取两者的最小值

---

#### 4.5 TCP拥塞控制 🔥🔥（大题核心）

**拥塞控制（Congestion Control）**：防止**发送方发送太多**导致**网络过载**（路由器队列溢出、丢包）

> **📌关键区别**：
> - **流量控制**：解决**发送方-接收方**之间的速度不匹配问题（接收方缓冲区满）
> - **拥塞控制**：解决**发送方-网络**之间的过载问题（网络链路/路由器队列满）
> - 两者关联：拥塞控制 ↔ [[进程调度]]（OS中对进程发送速度的调度机制异曲同工）

##### 4.5.1 四大会算法 🔥

| 算法 | 核心思想 | 触发条件 |
|------|---------|---------|
| **慢启动（Slow Start）** | 指数增长：cwnd每RTT翻倍 | 连接初始化、拥塞发生后 |
| **拥塞避免（Congestion Avoidance）** | 线性增长：cwnd每RTT+1 | cwnd达到ssthresh后 |
| **快重传（Fast Retransmit）** | 收到3个重复ACK立即重传 | 3个重复ACK |
| **快恢复（Fast Recovery）** | cwnd = ssthresh，进入拥塞避免 | 快重传后 |

##### 4.5.2 参数定义

| 参数 | 名称 | 说明 |
|------|------|------|
| **ssthresh（ssThresh）** | 慢启动阈值 | 区分慢启动和拥塞避免的阈值（门限值） |
| **cwnd** | 拥塞窗口 | 发送方根据拥塞状况可发送的最大数据量 |

##### 4.5.3 状态转移图（大题必会）🔥

```
                        │  超时（3个RTT未收到ACK）  │
                        │  cwnd = 1, ssthresh = 原cwnd/2  │
                        │  回到慢启动            │
                        └─────────────────────────┘
                              ↑
    慢启动 (cwnd=1,指数增长)  │  拥塞避免 (cwnd,线性增长)
    cwnd每RTT×2              │  cwnd每RTT+1
    ┌─────────┐              │  ┌─────────┐
    │         │              │  │         │
    │  cwnd    │              │  │  cwnd    │
    │ < ssthresh│             │  │ >= ssthresh│
    └────┬────┘              │  └────┬────┘
         │  cwnd >= ssthresh触发 │     │  3个重复ACK → 快重传
         │  进入拥塞避免          │     │  cwnd = cwnd/2, 进入快恢复
         ▼                      │     ▼
    ┌─────────┐              │  ┌─────────┐
    │ 拥塞避免   │              │  │ 快恢复    │
    │ 线性增长   │              │  │ 线性增长  │
    └─────────┘              │  └─────────┘
                              │
    状态转换总结表：
    ┌──────────────────┬──────────────┬──────────┬──────────┐
    │ 当前状态          │ 触发事件     │ ssthresh │ cwnd     │
    ├──────────────────┼──────────────┼──────────┼──────────┤
    │ 慢启动            │ 收到ACK     │ 不变     │ cwnd × 2 │
    │ 拥塞避免          │ 收到ACK     │ 不变     │ cwnd + 1 │
    │ 慢启动/拥塞避免    │ 超时       │ cwnd/2   │ 1        │
    │ 慢启动/拥塞避免    │ 3个重复ACK  │ cwnd/2   │ cwnd/2   │
    └──────────────────┴──────────────┴──────────┴──────────┘
```

##### 4.5.4 拥塞控制全过程示例（大题）🔥🔥

```
假设初始：cwnd = 1, ssthresh = 16

RTT1: 慢启动    → cwnd = 1 → 2
RTT2: 慢启动    → cwnd = 2 → 4
RTT3: 慢启动    → cwnd = 4 → 8
RTT4: 慢启动    → cwnd = 8 → 16（达到ssthresh）
RTT5: 拥塞避免  → cwnd = 16 → 17
RTT6: 拥塞避免  → cwnd = 17 → 18
RTT7: 3个重复ACK → 快重传+快恢复
        ssthresh = 18/2 = 9
        cwnd = 9（进入快恢复/拥塞避免）
RTT8: 拥塞避免  → cwnd = 9 → 10
RTT9: 拥塞避免  → cwnd = 10 → 11
...继续线性增长

假设后续超时：
        ssthresh = cwnd/2
        cwnd = 1（回到慢启动）
```

> **🔥大题评分关键**：必须准确写出每个RTT后的cwnd值，以及ssthresh的变化。这是408考研中最经典的大题类型。

#### 4.6 TCP延迟确认与Nagle算法 ⭐

**延迟确认（Delayed ACK）**：
- 接收方不立即发送ACK，而是等待最多200ms，看是否有数据要捎带回复
- 若超时仍未有数据要发送，则发送ACK
- 优点：减少ACK报文数量

**Nagle算法**：
- 发送方若有一个未确认的小报文，则等待确认到来后再发送更多数据
- 目的：减少小报文数量，提高网络利用率
- 与延迟确认配合使用时，可能产生"萨格纳克效应"（Silly Window Syndrome）

### 六、TCP拥塞控制与流量控制的对比 🔥

| 对比维度 | 流量控制 | 拥塞控制 |
|---------|---------|---------|
| **问题来源** | 接收方处理速度跟不上 | 网络链路/路由器容量不足 |
| **控制目标** | 不使接收方缓冲区溢出 | 不使网络过载（路由器队列溢出） |
| **控制依据** | 接收方通告的rwnd | 网络拥塞程度（丢包/延迟） |
| **窗口参数** | rwnd（接收窗口） | cwnd（拥塞窗口） |
| **控制方** | 接收方告知，发送方遵守 | 发送方自主判断 |
| **OS关联** | 进程缓冲区大小限制 | 进程发送调度策略（跨科目关联→[[进程调度]]） |
| **网络协议关联** | TCP首部"窗口大小"字段 | 通过丢包/重复ACK触发 |

> **📌跨科目关联**：TCP拥塞控制中，发送方的发送速率调度类似于操作系统中的[[进程调度]]——都要在资源有限的情况下实现公平性和效率的平衡。在OS中，进程调度决定CPU时间片分配；在网络中，拥塞控制决定数据发送速率。

### 七、TCP与UDP对比总结 🔥

| 对比项 | TCP | UDP |
|-------|-----|-----|
| **连接** | 面向连接 | 无连接 |
| **可靠性** | 可靠（ACK+重传） | 不可靠 |
| **传输方式** | 字节流（无边界） | 报文（保持边界） |
| **流量控制** | 有（滑动窗口） | 无 |
| **拥塞控制** | 有（慢启动等） | 无 |
| **头部开销** | 20字节+选项 | 8字节 |
| **通信方式** | 仅点对点 | 点对点、一对多、多对一、多对多 |
| **适用场景** | 文件传输、Web、邮件 | 音视频、DNS、游戏、实时通信 |

> **🔥大题考点**：为什么视频流常用UDP而不是TCP？因为UDP无拥塞控制，延迟低；TCP的拥塞控制会导致视频卡顿和抖动。实时应用更容忍丢包而非延迟。

## ⚖️易混淆概念对比

### 可靠传输 vs 面向连接

| 对比项 | 可靠传输 | 面向连接 |
|--------|---------|---------|
| **定义** | 数据不丢失、不重复、不乱序 | 通信前先建立连接，通信后释放连接 |
| **TCP具备** | ✅ 具备 | ✅ 具备 |
| **关系** | 面向连接≠可靠传输 | 可靠传输≠面向连接（如某些可靠UDP） |
| **关联文档** | [[05-传输层]] | [[05-传输层]] |

### 滑动窗口（流量控制）vs 拥塞窗口（拥塞控制）

| 对比项 | 滑动窗口（rwnd） | 拥塞窗口（cwnd） |
|--------|-----------------|-----------------|
| **控制目标** | 接收方缓冲区 | 网络拥塞程度 |
| **由谁决定** | 接收方 | 发送方 |
| **如何通告** | TCP首部窗口字段 | 发送方自行估算 |
| **变化方式** | 接收方实时调整 | 慢启动/拥塞避免算法 |
| **关联文档** | [[05-传输层]] | [[05-传输层]] |

### 三次握手 vs 四次挥手

| 对比项 | 三次握手（建立连接） | 四次挥手（释放连接） |
|--------|-------------------|-------------------|
| **报文数量** | 3个（SYN, SYN+ACK, ACK） | 4个（FIN, ACK, FIN, ACK） |
| **原因** | 可以合并SYN+ACK的确认 | TCP是全双工的，双方需单独关闭 |
| **携带数据** | 第三次握手可携带数据 | 前两次的ACK可携带数据 |
| **关联文档** | [[05-传输层]] | [[05-传输层]] |

## ⚠️考试高频坑点

### 坑点1：SYN和FIN消耗序号但不携带数据

> 【考试考法】"SYN报文段序号为100，确认后序号为多少？"
> 
> ⚠️ 常见错误：确认后序号仍为101（忘记SYN消耗1个序号）
> 
> ✅ 正确：SYN消耗1个序号，确认后序号 = 100 + 1 = 101

### 坑点2：慢启动是指数增长，拥塞避免是线性增长

> 【考试考法】"拥塞避免阶段cwnd如何变化？"
> 
> ⚠️ 常见错误：认为是指数增长
> 
> ✅ 正确记忆：慢启动=指数增长（每RTT×2），拥塞避免=线性增长（每RTT+1）

### 坑点3：3个重复ACK → cwnd减半，不是直接到1

> 【考试考法】"收到3个重复ACK后cwnd变为多少？"
> 
> ⚠️ 常见错误：cwnd变为1
> 
> ✅ 正确：3个重复ACK → 快重传+快恢复 → cwnd = 原cwnd/2，ssthresh = 原cwnd/2

### 坑点4：TCP和UDP的端口号范围

> 【考试考法】"熟知端口范围是多少？"
> 
> ⚠️ 常见错误：记错为0~65535或0~1024
> 
> ✅ 正确：0~1023为熟知端口，1024~49151为注册端口

### 坑点5：流量控制 vs 拥塞控制

> 【考试考法】"cwnd由谁决定？rwnd由谁决定？"
> 
> ⚠️ 常见错误：两者都由对方决定或都由自己决定
> 
> ✅ 正确：cwnd由发送方自行判断（基于网络状况），rwnd由接收方通告
